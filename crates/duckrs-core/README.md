# duckrs-core

`duckrs-core` is the engine of duckrs: the catalog, the built-in functions and casts, the binder and
logical planner, the optimizer, physical execution (including the CSV, JSON and Parquet readers and
writers) and the storage engine that reads and writes DuckDB database files. It ports most of DuckDB's
`src/` apart from `common`, `parser` and `main`: `src/catalog`, `src/function`, `src/planner`,
`src/optimizer`, `src/execution`, `src/parallel`, `src/storage`, `src/transaction` (in spirit) and
`src/logging`, plus parts of `extension/core_functions`, `extension/json` and `extension/parquet`. It
depends on `duckrs-common` (types, vectors, values) and `duckrs-parser` (the AST). It is used by
`duckrs-main` (the client: `ClientContext`, `DatabaseInstance`, settings, EXPLAIN), which the public
facade `duckrs` and the shell `duckrs-cli` build on.

The usual entry is the client in `duckrs-main` or the `duckrs` facade. The engine can also be driven
directly. This program binds, optimizes and runs a query against an empty in-memory catalog:

```rust
use duckrs_core::catalog::Catalog;
use duckrs_core::execution::run_plan;
use duckrs_core::optimizer::{OptimizerOptions, optimize};
use duckrs_core::planner::binder::Binder;
use duckrs_core::planner::column_binding_resolver::resolve_column_bindings;

fn main() -> duckrs_common::Result<()> {
    let catalog = Catalog::new("memory");
    let statement = duckrs_parser::parse_ast("SELECT 40 + 2 AS answer")?.remove(0);
    let mut binder = Binder::new(&catalog);
    let bound = binder.bind(&statement)?;
    let mut plan = optimize(bound.plan, OptimizerOptions::default());
    resolve_column_bindings(&mut plan)?;
    let rows = run_plan(plan)?;
    assert_eq!(bound.names, ["answer"]);
    assert_eq!(rows.get_value(0, 0).try_to_string()?, "42");
    Ok(())
}
```

## How it works

### A query, from AST to result

The client (`duckrs-main`, around `ClientContext` in `crates/duckrs-main/src/lib.rs`) does these steps
for a statement that returns rows.

1. **Parsed AST.** `duckrs-parser` turns the SQL text into `ast::Statement` values.
2. **Binder** ([`planner/binder`](src/planner/binder)). `Binder::with_options(&catalog, options)` gets
   the catalog of the transaction (a `Fork`), the session values (settings, variables) and prepared
   parameters. `bind_statement` dispatches on the statement kind (SELECT, INSERT, UPDATE, DELETE,
   MERGE, CREATE TABLE, COPY, CALL; anything else is `unported`). Binding resolves names against the
   catalog through a `BindContext` of `Binding`s (the columns each FROM entry makes visible), gives
   each FROM entry a table index, and turns expressions into `BoundExpr`. A column is a
   `ColumnBinding { table_index, column_index }`. Functions are resolved by
   `function::binder`, which picks an overload and adds implicit casts. Constant expressions are
   folded with the expression executor (`evaluate_scalar`).
3. **Logical plan.** The binder plans as it binds: the result is a tree of `LogicalOperator`s in
   `BoundStatement.plan`, for example `Projection` over `Aggregate` over `Filter` over `Get`. Before
   returning, `bind` calls `subquery::flatten_subqueries`, which turns correlated subqueries into
   joins (DELIM joins, as in C++), and keeps the plan's output columns as they were.
4. **Optimizer.** `optimize_timed` rewrites the plan pass by pass in the order listed above. Plans
   still use `ColumnBinding`s at this point, so passes can move operators without renumbering columns.
5. **Column binding resolution.** `resolve_column_bindings` replaces each `ColumnBinding` by the
   position of that column in the child operator's output.
6. **Physical plan.** `execution::create_plan` first pushes join filters into scans
   (`join_filter::push_join_filters`), then `create_physical` maps each `LogicalOperatorKind` to a
   physical operator (for example `Join` with conditions to `join::PhysicalJoin`, `Insert` to
   `PhysicalInsert`). The client puts a `PhysicalResultCollector` (a sink) at the root.
7. **Pipelines.** `build_pipelines` walks down from each sink. A pipeline is a source, the streaming
   operators above it, and a sink. A join is a sink for its build (right) side, so the build side's
   pipeline is collected first and runs before the probe pipeline that streams through the join. An
   operator that is both source and sink (an aggregate, an ORDER BY, an INSERT) ends one pipeline and
   starts the next. RIGHT and FULL joins get an extra pipeline for their unmatched rows. Only the last
   pipeline feeding a sink calls `finalize`.
8. **Execution.** `execute_plan_with(root, threads)` runs the pipelines in order. A pipeline whose
   source has `parallel_source` (for example a table scan, one row group per morsel), whose operators
   are all `parallel_operator` and whose sink is `parallel_sink` runs on `std::thread::scope` threads:
   each claims morsels from an atomic counter, sinks into a local state, and the states are joined in
   `combine_local`. Other pipelines run on the calling thread: `get_data` until it returns `None`,
   pushing each chunk through `execute_stateful` (which can return `HaveMoreOutput` to be called again)
   and `final_execute` at the end. Data moves as `DataChunk`s of vectors from `duckrs-common`.
   Operators that can spill ask the query's `QueryMemory` (`temporary.rs`) before holding more bytes.
9. **Result.** The collector holds the rows as a `ColumnDataCollection`, which the client returns with
   the names and types of the `BoundStatement`.

### Reading and writing a DuckDB file

- **Opening.** `storage::load_database(path, catalog, read_only, encryption)` opens a
  `SingleFileBlockManager`. A file is three 4 KiB headers (one main header, then two database headers,
  of which the one with the higher iteration counts) followed by blocks, each starting with a
  checksum. A `BufferManager` caches blocks. `metadata::load_free_list` reads the free list,
  `wal::read_records` reads the `.wal` file next to the database, and `checkpoint::read_catalog`
  deserializes the catalog entries of the last checkpoint (through `serialization::generated` and
  `convert.rs`, which produce the same AST the parser would). A `wal::Replay` adds the entries to the
  catalog and then applies the committed log records. Records after the last `WAL_FLUSH`, or a record
  cut halfway, are what a crash leaves and are ignored.
- **Scanning.** Table rows stay in the file. A table's `TableSource` (`table_data.rs`) reads row groups
  when a scan asks for them, decoding each column segment with the scan for its codec in
  `compression.rs`. Zone maps and filters let a scan skip row groups and read other columns only for
  rows that pass.
- **Committing.** The engine has no undo log. `log_writer.rs` compares the catalog with what is durable
  and writes the difference as C++'s WAL records. A commit that did more than append rows deletes all
  rows of the table and inserts them again. Large appends are written to blocks before the commit
  (`writer::write_ahead`, `OptimisticDataWriter` in C++), and the log records where those row groups
  are.
- **Checkpoint.** `writer::write_checkpoint` writes the whole database into blocks the last checkpoint
  does not use, then writes a new database header. A crash before the header leaves the old
  checkpoint intact. Each column segment gets the compression C++ would pick (`DetectBestCompressionMethod`
  by analyze score: RLE, bit-packing, Roaring, DICT_FSST, ZSTD, and others by storage version), and the
  segments are written as C++ lays them out. Indexes are rebuilt from the rows at each checkpoint
  (`index_data.rs`) so that C++ can read them. duckrs builds its own keys from the rows instead.

### Module dependencies

The modules inside `duckrs-core` form one dependency cycle (this was measured). The binder evaluates
constants with the executor (`planner/collation.rs` uses `execution::expression_executor`). The
executor runs plans from the planner. `catalog` and `storage` call each other. `function` and
`planner` use each other. Because of this the crate isn't split further yet; see `../CLAUDE.md` §1 and
`RUST_PORT_PLAN.md` §3 for the planned crates. The client used to be the module `client`; it is now the
crate `duckrs-main`, and nothing in `duckrs-core` uses it.

## Notes for contributors

- **Layering** (`../CLAUDE.md` §1). Don't move files between the top-level modules (`catalog/`,
  `execution/`, `function/`, `optimizer/`, `planner/`, `storage/`) and don't start the crate split on
  your own. Put new code in the module that will become its crate, and don't add dependencies that
  point upward in `common → parser → catalog → function → planner → optimizer → storage → execution →
  main`. Where lower code needs higher code, pass a trait or a callback. Engine code must not use the
  client (`duckrs-main`).
- **Typed kernels** (§2). Physical operators and scalar or aggregate kernels work on typed vector data
  (`flat::<T>()`, `data_mut::<T>()`, the unary/binary executors, `UnifiedVectorFormat`), not
  `Vector::get_value` / `set_value` per row. `Value` per row is fine for the catalog, binder, EXPLAIN and
  errors. Don't add per-row `Value` code to operators that still have it (for example `PhysicalUnnest`).
- **`unsafe`** (§3). New `unsafe` in this crate is allowed only under `src/storage/` (I/O and
  compression kernels), with a `// SAFETY:` comment above each block. Existing `unsafe` elsewhere
  (`optimizer/extract_pushdown.rs`, `execution/temporary.rs`, `execution/group_table.rs`) is not to be
  extended.
- **Port headers.** Start each file with `// Ported from duckdb/<path> @ rust-port-baseline`, or
  "Ported in spirit from" where the design differs. Doc comments name the C++ class or function in
  backticks (`` `PhysicalHashJoin` ``).
- **Errors.** Error messages are copied word for word from C++. For SQL DuckDB supports that is not
  ported, return `crate::unported("...")` rather than a message of your own.
- **Generated files.** `catalog/defaults_table.rs` (`tools/generate_defaults.py`) and
  `storage/serialization/generated.rs` (`tools/generate_serialization.py`) are generated; edit the
  generator instead.
- **Gate.** `cargo clippy --workspace --all-targets -- -D warnings` must stay clean.
